### Consequence nobody had connected: the LED cache lies about dropped sends

`live/LiveBoard.java:85-86` and `:103-104` write the dedupe cache **before** calling `send()`, and `send()`
has no success signal. So every one of those 11 dropped messages left `lastLed`/`lastName` asserting the
Pacer shows something it never received. `invalidate()` has exactly one caller (`PacerController.java:201`,
reached only from `repaintAll()`), so nothing re-asserts it — the board stays wrong until that switch's
state happens to change again.

That is a concrete, log-backed mechanism for "random weirdness on the board", and it is cheap to fix:
send first and cache only on success, or count failures and `invalidate()`.

## Verdict

No auditor found a line of code that can throw inside a Bitwig callback — the tick chain is consistently bounds-checked and `doesExist()`-guarded, and the two explicit `throw`s in the extension are unreachable. What the code *does* contain is a single point of failure that converts any one transient exception into a permanent, silent half-death: `PacerControllerSetup.tick()` re-arms the 40 ms heartbeat only as its last statement, with no `try/finally`, and `HostImpl.scheduleTask` is a bare delegate that catches nothing. One bad frame — from Bitwig, a project switch, a track vanishing under a bank — and the loop stops forever while switch presses keep working. That is exactly the shape of "it's been working okay but I still had some random crashes": not a crash dialog, but LEDs frozen on stale colours, count-ins that never fire, a fade parked mid-ramp leaving loops silent, and no trace except one line in a console nobody opened. **Fix the `finally` before the session, and open Help > Show Controller Script Console** — if a throw is happening, the stack trace is already being printed there and will name the real culprit in one run.

## The crash suspects, ranked

### 1. The 40 ms tick re-arms only on the success path

**Found independently by 8 of the 17 auditors** (threading, exception-safety, bitwig-lifecycle, flush-cost, looper-state, modes-live, config-settings, test-coverage) — the strongest corroboration in the whole audit.

**Mechanism.** `bitwig/src/main/java/dev/pacer4bitwig/pacer/PacerControllerSetup.java:323-332`:

```java
private void tick ()
{
    if (!this.running) return;
    this.controller.tick ();      // looper.tick(), fx.tick(), paint()
    this.restoreName ();
    this.dawMode.flushLeds ();
    this.requestFlush.run ();
    this.host.scheduleTask (this::tick, TICK_MS);   // line 331 — the ONLY re-arm
}
```

There is no other re-arm: `startup()` at line 301 is the only other entry, `running` is set true once at line 288 and never re-checked to restart, and the entire main source tree contains no `try/catch` outside `fx/SnapshotBank.java:164` and `:187`. `HostImpl.scheduleTask` was disassembled from DrivenByMoss-26.6.5 and has no exception table. Note the asymmetry: DrivenByMoss *does* guard the flush path (`AbstractControlSurface.flushHandler` catches RuntimeException and logs "Crash during flush."), so flush-side code survives a throw and tick-side code does not.

**What you would observe.** Switch presses still work (they are MIDI bindings). LEDs still react to presses and to Bitwig state changes, because Bitwig calls `flush()` on its own — but they stop *animating*: blinking freezes, and all SysEx colour/name painting stops dead, because `PacerController.paint()` (PacerController.java:154) runs periodically only from the tick. The Pacer's display keeps the last CC readout instead of the mode name. Count-ins never convert to a recording. "Match the first loop" stops. Quantized mutes never land. Exclusive arm stops disarming. **And a fade in progress freezes mid-ramp with the originals never restored** — your loops sit at whatever volume the ramp reached. Only reloading the extension recovers it.

**Fix** (5 minutes, zero risk):

```java
private void tick ()
{
    if (!this.running) return;
    try {
        this.controller.tick ();
        this.restoreName ();
        this.dawMode.flushLeds ();
        this.requestFlush.run ();
    } catch (final RuntimeException ex) {
        this.host.error ("PACER Looper tick failed", ex);   // rate-limit this
    } finally {
        if (this.running)
            this.host.scheduleTask (this::tick, TICK_MS);
    }
}
```

Do the same around `startup()` — `GenericControllerExtension.init()` schedules it through the same unguarded path, so a throw there means the loop never starts at all and the extension is inert from boot. Also wrap `fx.tick()` separately in `PacerController.java:584-590` so a failing FX resolve cannot take `looper.tick()` down with it. Rate-limit the `host.error` call or a persistently throwing tick logs 25 times a second.

**Caveat, stated plainly:** this is the amplifier, not a demonstrated fault. If nothing is throwing, this fix changes nothing you can see. It is still the first thing to do, because it costs nothing and it is the difference between one dropped frame and a dead rig mid-song.

### 2. A fade can end without restoring the volumes — and `exit()` never restores them

`LooperController.java:1017-1024`, `:1048` (`restoreFadeVolumes`), `PacerControllerSetup.java:313-320` (`exit()`).

**Mechanism.** `VolumeFade` holds the *only* copy of the pre-fade volumes (`LooperController.java:988`), and `restoreFadeVolumes()` is the only writer-back — reachable only from `updateFade` inside the tick. Three ways out skip it:

- The tick dies (suspect 1). Loops stay at the faded level.
- `exit()` lands mid-fade — project close, controller disabled, `mvn install` hot-reload. `LooperController` has no shutdown hook at all.
- An un-started fade-in. `toggleFade` writes every loop track to volume 0 *before* the ramp exists (`LooperController.java:991-998`), and `updateFade` skips the restore both when the transport stops before the ramp started (`:1019`) and when the transport runs but no loop is playing (`:1023-1024`). So: transport running, loops stopped, hold MIX SW B (FADE_IN), then tap STOP_ALL inside the quantization window → every loop track sits at 0 with the fade alive forever.

**What you would observe.** Loops silently at zero or half volume, with the fade switch blinking. It *is* recoverable in-session — press the blinking fade switch again ("Fade cancelled", `:967`), RESET (`:1167`) or CLEAR_ROW (`:1147`) — but nothing signposts that, and if you save the project in that state Bitwig persists the faded faders.

**Fix.** Give `LooperController` a `shutdown()` that calls `restoreFadeVolumes()` and `applyPendingMutes(entry -> true)`, called from `exit()` before `super.exit()`. In `updateFade`, restore whenever a fade-in's ramp never started, not only on transport stop, and have `stopAll()` settle a pending fade the way `clearRow`/`reset`/`prepareForTrackScroll` already do.

### 3. DAW-mode held function repeats at 10 Hz forever if the release CC is lost

`daw/DawModeController.java:141-150` and `:167-174`. Found independently by three auditors (exception-safety, bitwig-lifecycle, midi-load/daw-mode).

**Mechanism.** `repeat()` re-arms itself every 100 ms and exits only on `!connected`, `!held[cc]` or a stale generation. `held[cc]` is cleared only by the matching release CC (`:143`) or by toggling the DAW-mode setting (`:75`). Lose the release — leave the DAW preset mid-hold, USB re-enumerate — and REWIND / FAST_FORWARD / TRACK_NEXT / PATCH_NEXT keep firing indefinitely.

**What you would observe.** The playhead scrubbing away on its own, or the track/device selection walking to the end of the project, with nothing on the Pacer sustaining it. **One press-and-release of the same switch kills it** (`++holdGenerations[data1]` at `:144` orphans the chain) — it is not unrecoverable.

**Is this you?** Only if you turned on *Serve the Track and Transport presets*. It defaults to **off** (`PacerConfiguration.java:318`), it needs port 2 assigned, and it needs the Pacer sitting on its built-in Transport/Track preset — which is mutually exclusive with the looper preset you play on. **Check whether you enabled it.** If not, rule this out entirely.

**Fix.** Add `Arrays.fill (this.held, false)` next to the `sentLeds` reset in `handleSysex` (`:188`). Do **not** add the 5-second cap that was proposed — holding fast-forward to scrub a long arrangement legitimately exceeds five seconds, and the cap would kill the repeat under your foot. Also wrap `perform` at the `handleMidi` call sites (`:139`, `:147`) so a throw cannot escape into the MIDI callback.

### 4. Seven `scheduleTask` callbacks with no liveness gate

`LooperController.java:856, 1218, 1223, 1251, 1252, 1288, 1304` and `command/TapHoldCommand.java:140`, versus `PacerControllerSetup.java:293-295` which correctly guards its retries with `if (this.running)`.

## MIDI load

**No. You are not overloading the MIDI, and it is not close.**

Message sizes (`live/PacerSysex.java:188-196`): LED SysEx = 26 bytes, name SysEx = 18 bytes, CC = 3 bytes. Tick = 25 Hz.

| Condition | Messages/s | Bytes/s |
|---|---|---|
| Steady state, nothing changing | **0** | **0** |
| Transport running, loops playing | ~5 CC/s | ~15 |
| Worst realistic live case* | ~73 | ~320 |
| Measured hardware ceiling (`docs/PACER-MAP.md:101`) | ~3300 | — |

\* 120 BPM 4/4, beat-synced LEDs on, count-beats on, a loop recording, a fade running, DAW mode on, stomping at 4 presses/s: ~66 CC/s (beat counter 4, five BLINK_FAST loop switches 40, fade 4, DAW LEDs ≤10, presses ~8) + ~6.5 SysEx/s.

That is ~10% of a 31250-baud DIN cable and a rounding error on USB. The dedupe layers all hold: `LiveBoard.setLed` drops unchanged writes on an int key (`live/LiveBoard.java:83-88`), DrivenByMoss's light state only emits a CC when the code changes, and `DawModeController.flushLeds` dedupes against `sentLeds` (`:117-124`). Steady state genuinely sends zero bytes.

**The real constraint is not throughput, it is trickle.** `LiveBoard`'s own javadoc says a burst reads as one brief flash but a few messages per second holds `LOAD SYS` on the display and hides the mode name. Two paths violate that:

- **The LED test on every load** (see Correctness, startup). ~10 SysEx per second for ~5 seconds, every project open and every `mvn install`.
- **`restoreName()`** re-writes the mode name after each press — a press per beat produces a name message per beat.

**Uncapped paths:** exactly one, `DawModeController.repeat` — and it emits **no MIDI** (`perform` only calls host APIs, `setLed` is change-gated). Every other path is bounded. `surface.forceFlush()` on mode change costs 20 CCs and 10 one-shot tasks, doubled on a preset announcement because `PacerControllerSetup.java:240` and `PacerController.java:576` both fire it — worth removing one, not a load problem.

## Correctness bugs

### Startup / configuration

- **The LED test runs on every extension load.** `PacerControllerSetup.java:170` is the only observer in `createObservers()` without an `if (this.running)` guard, and `AbstractControllerSetup.init()` ends with `notifyAllObservers()`, which fires every observer whose key is not in the never-populated `dontNotifyAll` set. Result: a spurious "LED test: white, red, green, amber, blue, purple" popup and ~5 seconds of the board cycling colours over `applyStartupMode()`, on every project open and every hot-reload. **Verified high by all three verifiers.** One-line fix. *Do not* "consistency-fix" `EXPRESSION_1`/`EXPRESSION_2` at `:187-188` — those are deliberately unguarded and must stay so.
- **Both expression pedals keep the Looper mode's targets when a project starts in another mode.** `PacerController.java:126-130` (`applyStartupMode`) never runs `modeListener`, so the binding made during `registerContinuousCommands` (`PacerControllerSetup.java:259`, while `ModeState` is still at `new ModeState(Mode.LOOP)`) is never replaced. Open a project last left in FX and EXP 1/2 drive the selected track's volume and the **master fader** instead of remotes 7/8 — and because `bind(IParameter)` replaces the binding, the intended target is not merely shadowed, it is dead. Worst case is CUSTOM, whose defaults are NONE/NONE: pedals you configured to do nothing still ride the mix. **Verified high by all three verifiers.** Fix: `this.bindPedal (0); this.bindPedal (1);` in `startup()` right after `applyStartupMode()`.
- **Custom mode: a hold-only switch is invisible but still fires.** `PacerConfiguration.java:431` resolves the AUTO colour from the *tap* action alone, and `SwitchColour.java:85` maps `Action.NONE` to `PacerColour.OFF`. Set SW 3 tap = Nothing, hold = Clear all loops in the row, and you get a dead-black switch that deletes your loops. Fix: fall back to double-tap then hold when tap is NONE.
- **`initPedals` indexes `EXPRESSION_DEFAULTS` by mode ordinal with no bounds guard.** `PacerConfiguration.java:499`, where the constructor at `:281-288` guards the same table and says why. Harmless today (both are 5); adding a sixth `Mode` throws `ArrayIndexOutOfBoundsException` during `init()` and the extension fails to load. Dev trap only.
- **`LoopSwitchCount.SIX` ("SW 1-6") can never differ from FIVE.** `looper/LoopSwitchCount.java:26`; `SwitchRole.java:38-39` returns MODE_SWITCH for index 5 before any board is read. Fix the docs, **not** the enum — renaming a label resets stored settings to the default.

### Switch dispatch (modes)

- **`TapHoldCommand` re-reads `tapOnPress` on release, so a press that changes the mode can fire a second action.** `command/TapHoldCommand.java:156` vs `:123`. Turn off "Loop switch fires on press", then pick Looper from the mode menu: the release also runs `loopSwitchTap(0)` and starts a recording on loop 1. Also fires for any `MODE_*` action on a custom switch. Latch the answer at DOWN in a `tapFiredOnPress` field. There is no `TapHoldCommandTest` at all.
- **`release()` re-reads `role()`, so a mode change mid-press drops the release.** `PacerController.java:355`. In hold-to-record, a take started by holding SW 1 is never closed if the other foot taps SW 6 first. Same root cause strands `momentarySwitches` — `PacerController.java:362` does `Arrays.fill(..., null)` on mode change, so an FX MOMENTARY switch held across a mode change stays latched on. Latch the role at press time; that fixes all three.
- **`presetAnnounced` forces `Mode.LOOP` on every preset selection** and bypasses `modeChanged()`. `PacerController.java:570-578`. With one preset, the `PresetKind.FX` branch is unreachable from current hardware (`tools/pacer-preset.mjs:29` sends 127), so re-selecting D1 always drops you back to the Looper board — no notification, no `setProjectMode`, and the mode menu is left open if it was. Keep the FX branch (back-compat for an old D2 preset still on your unit); make the LOOPER-kind announcement a pure resync.
- **After a non-menu mode change, the first painted frame uses the old mode's cached colours.** `PacerController.java:365` calls `paint()` before any flush has run for the new mode. Low — one tick of stale colour on lit switches, plus a few extra SysEx.
- **`MODE_*` actions have no `actionLed` case anywhere**, so a custom switch carrying one rests dim and never lights. `PacerController.java:551` → `LooperController.java:548` `default -> LedState.DARK`.

### Looper

- **`clearLastLoop` eats other rows' undo history.** `LooperController.java:824-841` drains `recordHistory` with `pop()` and `continue`s past entries belonging to other rows, discarding them. Press it in a row whose history is exhausted and every other row's entries go with it. Loops are not deleted — only the undo index. Walk the deque with an `Iterator` and `remove()` only what you act on.
- **`closeWhenRecording` is not cleared when a new recording starts on that switch.** `LooperController.java:181`. Hold-to-record + count-in: release during the count-in, cancel, re-press within 1 s → the new take is closed the instant it starts. Clear it next to `holdRecording[switchIndex] = false`, and also in `recordNextLayer` (`:785-801`), which the proposed fix misses.
- **Double/halve acts on whatever clip the cursor points at 150 ms later.** `LooperController.java:845-874` never re-checks that `model.getCursorClip()` is still the slot it selected. Any selection change inside the window — including a loop-switch press with "Select on press" on — applies `duplicateContent()`/`setLoopLength(length/2)` to another track's clip while the notification names the original. Only reachable if you assigned DOUBLE/HALVE to a jack or custom switch; they are on no default board.
- **A pending count-in has no timeout while the transport runs, and targets an absolute beat.** `LooperController.java:697`. A backwards playhead relocation, or an arranger loop that wraps before the target (2-bar count-in started in the last bar of a 4-bar loop → target 19.5, past the loop end), pins the switch in "record queued" forever. Tapping the same switch cancels it, so the blinking switch *is* the escape — but nothing says so. Add a wall-clock ceiling and cancel on a backwards jump. Note `pendingMutes` is **not** affected — `LooperController.java:920` is `!running || position >= entry[1]`, so a stop flushes them.

### FX

- **`storeSnapshot` writes an all-NaN capture as a stored snapshot.** `FxController.java:488-498`. When every switch resolves to `FxTarget.NONE` (a "Pacer" page mapping none of remotes 1-6, or a track with no page and no devices), you get "Guitar: snapshot 1 stored", a slot that reads as occupied forever (`encode()` emits `",,,,,"`, so `isStored` stays true), and a recall that silently does nothing. Reject an all-NaN capture.
- **`recallSnapshot` reports success and persists the advanced index even when it applied nothing.** `FxController.java:439-447` and `:471-484`. In the window after a focus change, before `followRemotePage` gets Bitwig onto the page, one snapshot press is a silent no-op that still says "snapshot 2". Count applied values; move `next()`/`saveBank()` after a recall that did something.
- **`assign()` reports success for a track the FX bank cannot see.** `FxController.java:331-337` has no `else` on `position < 0`. Assign a return bus or the master (the selection cursor follows them; the FX bank is 64 regular tracks) and you get "Instrument A is now Reverb Bus" and a dead slot. Because `ASSIGN_A` is destructive, it also overwrites a working assignment.
- **Expression pedals can write to the wrong remote page for up to 500 ms after a focus change.** `FxController.java:204-208` guards on an index comparison between a stale `this.remotePage` and a fresh `getSelectedRemotePage()`, and `followRemotePage` pushes the stale index onto the new track. Only bites when two instruments have their "Pacer" page at different indices. Set `this.remotePage = -1` in `pointCursor`.
- **`followFocus` rescans all 64 track names every 40 ms when the instrument's track is missing.** `FxController.java:362-373` — the retry throttle is armed only inside `pointCursor`, which is skipped on failure. ~1600 cached reads/s forever, in every mode. Cheap and harmless but it is a dead guard; arm it on every attempt.

### Flush cost (not fatal, but avoidable)

- `LooperController.java:484-487` computes `getSelectedTrack()` and `selectedHasLoop` for every ACTION switch, including ones that return a constant. `LooperController.java:297` rebuilds the whole loop row four times per flush for the beat counter. Both are cached in-process reads, so this is tidying, not a hazard.
- `PacerController.java:174` — `paint()` **does** query Bitwig in SONG mode (`getRowDisplayName()` → `sceneBank.getScrollPosition()` plus a `split(",")` per call). One cached read; the CLAUDE.md sentence is what needs fixing, not the code.

### Editor (Pacer Studio)

- **Cancelling verification reports "Wrote and verified" and returns `true`.** `editor/src/app/operations.ts:462-478` swallows the abort via `isAbortError` and then takes the success branch with `labels` built from every slot, not the verified ones. Track the abort, warn, return `false`.
- **A global-settings message with a non-7-bit data byte throws during React render.** `editor/src/pacer/global.ts:135-142` is the only encoder that does not clamp; `sysex.ts:42` throws. First reached at `TopBar.tsx:83` (always mounted), so the page goes blank on the first global edit after importing a corrupt .syx. Reject non-7-bit at the parse boundary — and check `index`/`obj` too, not just `elm`/`value`.
- **LED colour names are one family off** from `PacerColour.java` and the Pacer manual: 0x0B is "Lime" in the editor and "Green" everywhere else, 0x0D is "Green" here and "Dark green" there. Byte values agree; only labels and swatches drift. Pick one vocabulary — note the extension is itself inconsistent (0x07 is "Amber" in *Loop colour*, "Gold" in *Custom mode*).

### Tools (hardware safety)

- **`pacer-send.mjs` accepts a truncated pre-write backup, then overwrites the slot anyway.** `tools/pacer-send.mjs:47-52` gates only on `backup.length === 0`. Commit 5318fd0 added count/checksum/slot gates to `pacer-backup.mjs` and did not touch this one — the script that destroys the thing being backed up. Short dumps are real and checksum-clean (`backups/pacer-full-2026-09-16T07-18-17-INCOMPLETE.syx`: 4193 messages, 0 bad checksums). Require `backup.length === 189` and `m[7] === idx` before opening the output port; factor it as a shared `assertCompletePreset` in `lib/pacer.mjs`. The input file at `:31` needs the same count check.
- **`led-live-colour.mjs --slot` writes cmd 0x01 to EEPROM with no backup and no confirmation**, and its only notice prints *after* `sendMessage`/`closePort`. `tools/led-live-colour.mjs:25, 39-44`. The script's stated purpose (index-0 live writes) needs no stored slot — delete the branch.
- `tools/pacer-send.mjs` has no SIGINT/`try-finally` guard around its 1.9 s send loop, so a Ctrl-C leaves a half-written preset with no message saying so. **Leave `DELAY_MS = 10` alone** — the ~3300 msg/s measurement was against preset index 0 (RAM); the EEPROM path has never been measured.
- `tools/led-live-colour.mjs:22-26` builds SysEx from unvalidated `--switch` / `--colour`: `--switch 11` emits a NaN checksum coerced to 0, `--colour 0x7f` puts a 0x80 status byte mid-SysEx. Validate the ranges. Do **not** make `checksum()` throw — it is the engine of `isValidPacerMessage`, which two scripts use as a gate.

## Completeness critic — what the sweep missed

## 1. Crash mechanisms nobody investigated

- **MIDI output port death mid-session — and it is in the user's logs.** Not one of the 17 auditors considered what happens when `IMidiOutput.sendSysex` targets a port Bitwig has lost. `BitwigStudio.log:834` and `BitwigStudio-previous-run.log:8433` both show `MIDI Output Error: PACER: Could not send MIDI message`, each immediately followed by **exactly 11** `couldn't send midi sysex because the outport isn't opened` — which is `repaintAll()`'s 10 LEDs + 1 name. The extension's SysEx is being dropped on the floor, twice in two consecutive sessions.
- **The dedupe cache records failed sends as successful.** `live/LiveBoard.java:85-86` sets `this.lastLed[switchIndex] = key;` *before* `this.send(...)`, and `send`/`setName` have no success signal. A port hiccup that drops a burst leaves `lastLed`/`lastName` claiming the device shows something it never received, and nothing ever re-asserts it (`invalidate()` has 3 callers, none periodic). **This is a concrete, log-backed mechanism for "random weirdness" and no auditor found it.** Fix: send first, cache only on success, or add a failure counter that triggers `invalidate()`.
- **USB re-enumeration storm.** The log is littered with `libusb: error [init_device] device 'USB\VID_0000&PID_0002\6&5280D8E&0&4' has invalid descriptor!` (17+ occurrences) and `windows_submit_transfer ... transfer HANDLE is NULL`. The Hydrasynth loses its port too. Nobody asked whether the Pacer's port survives this, or whether the four DrivenByMoss-shaded extensions each initialise libusb/JNA independently.
- **Audio engine native crash.** `BITWIG_ENGINE.info` = `ExceptionCode:0xC0000005` (access violation) at `0x00000001400468D4`, with a 395 KB minidump at `BITWIG_ENGINE.mdmp` (2026-09-18 01:51). Nobody looked. The engine is a separate native process — a Java extension cannot directly cause this, which is itself worth confirming (`engine.log` shows `ysusb_asio64.dll`, the Yamaha Steinberg USB driver, loaded).
- **GC/JVM.** Bitwig 6.0.11 runs `-XX:+UseZGC -XX:+ZGenerational -Xms300m -Xmx3g`. Nobody sized the per-flush allocation against that (LiveBoard builds a hex `String` per SysEx; `getRowStates()` allocates 4×/flush; `LedClock` records). ZGC is pauseless so this is probably a non-issue — but "probably" is not a finding, and it is the only thing that would explain *timing* glitches rather than logic glitches.
- **Four ~14.5 MB DrivenByMoss uber-jars in one JVM.** `DrivenByMoss`, `ElectrixTweaker`, `Pacer4Bitwig`, `Shove4Bitwig` are all installed. Each bundles JNA + purejavahidapi natives. `System.loadLibrary` of the same native from two class loaders is a documented `UnsatisfiedLinkError` shape. build-ci noticed the bloat but explicitly declined to investigate the runtime consequence.
- **Nektar's own `PACER.control.js` — not present.** `C:\Program Files\Bitwig Studio\resources\controllers\Nektar\` does not exist on this machine, so the CLAUDE.md port-contention warning is moot here. Rule it out and stop citing it.
- **Bitwig's threading model was assumed, never confirmed.** Three dimensions (threading, exception-safety, daw-mode) each concluded "single controller thread, so the non-volatile fields are fine" — all by reasoning, none by evidence. `PacerConfiguration` marks ~30 fields `volatile` while `DawModeController` assumes it needn't; one of those two is wrong.
